# CLS-5013: gobco fork with module-wide branch coverage

## Overview

Turn the module-mode prototype into a maintained fork of `rillig/gobco` (BSD-2-Clause, base `7a09995`).
The fork adds a module mode: one command instruments every package, runs one `go test`, and reports
branch or condition coverage for the whole module, including hits from other packages' tests and from
integration tests. Upstream needs one run per package, each with its own module copy and its own type
check of every dependency from source; the prototype runs in about the time of a plain `go test`.

## Architecture & Design

**Two modes in one binary.**

- Single-package mode (no `-module`): upstream behaviour, unchanged except the summary line format.
- Module mode (`-module`): new.

```
gobco -module [-branch] [-exclude pattern]... [-threshold pct] [-test opt]... [packages]
```

**Module mode flow** (`module.go`, `runModule`), run from the module root:

1. `go list -m -f '{{.Dir}}\t{{.Path}}'` gives the module root and path.
2. One `go list -find -e -f '{{.ImportPath}}\t{{.Dir}}'` call over the package arguments (default
   `./...`) gives the packages to instrument. A second call over the `-exclude` patterns gives the
   packages to leave out of the report.
3. `go list -export -deps -test ./...` fills a map of import path to export data file. It runs
   without `-e`, so a package that does not compile stops the run with the compiler's message. One
   `importer.ForCompiler(fset, "gc", lookup)` serves all packages.
4. Each package gets a fresh instrumenter. Instrumented files go to `<tmpdir>/overlay/<index>/` and
   are mapped in `<tmpdir>/overlay.json`. The registry package `gobcoreg` is mapped to
   `<module root>/gobcoreg/gobcoreg.go`, which does not exist on disk.
5. One `go test -overlay <tmpdir>/overlay.json -vet=off -count=1 <-test options> ./...` in the module
   root, with `GOBCO_STATS_DIR=<tmpdir>/stats`.
6. Merge: the baseline is each instrumenter's own condition list with zero counts. Every
   `<package index>.<pid>.json` in the stats directory adds its counts by condition index. gobco
   chooses the name and writes it into the injected code, so the two sides cannot disagree.
7. Report, then threshold check.

**Design decisions.**

- The baseline in step 6 comes from the instrumenter, not from the stats files. A package that no
  test binary links writes no file, and must still count as uncovered.
- `-exclude` removes packages from the report, the totals and the threshold. Excluded packages are
  still instrumented, so their test binaries still flush the counters of the packages they exercise.
  The prototype computed its figure the same way.
- Template variants: `gobco_fixed.go` keeps the shared code. `filename()` and `finish()` move to
  `gobco_single.go` (upstream bodies) and `gobco_module.go` (prototype bodies plus the registry
  `init`). The instrumenter writes one of the two.
- One `TestMain` template for both modes: it ends with `gobcoCounts.finish(0)` instead of
  `gobcoCounts.persist()`. In single mode `finish` is `persist`.
- Package patterns use `go list`, which also removes duplicates. From oliveagle `fa620c2` we take the
  idea of `expandRecursive` and the report format, not its code for duplicates (it edits a slice
  while ranging over it), its module copy, or its `--` separator.
- Counters are `int64` fields incremented with `atomic.AddInt64`. The JSON format does not change.
- The threshold compares exact integers (`covered*100 < threshold*total`), not the rounded figure.

## Implementation Tasks

1. Apply the prototype patch `gobco-module-mode.patch` with `git apply`.
2. In `go.mod` set `module github.com/artem-panasenko/gobco`. Replace the import path
   `github.com/rillig/gobco` in `testdata/testmaintest/add_test.go` and
   `testdata/pkgname/black_box_test.go`. Set `version.go` to `1.4.0`. Do not touch `LICENSE` or the
   issue links in comments.
3. Templates:
   - `templates/gobco_fixed.go`: remove `filename()`, `finish()`, the registry import and the `init`.
     Keep everything else as upstream.
   - New `templates/gobco_single.go`: upstream `filename()` (reads `GOBCO_STATS`) and upstream
     `finish()` (calls `persist`).
   - New `templates/gobco_module.go`: the prototype's `filename()` (reads `GOBCO_STATS_DIR`),
     `init` that registers `gobcoCounts.persist`, and `finish()` that calls `gobcoreg.Flush()`.
   - `templates/gobco_no_testmain_test.go`: upstream body, last counter call changed to
     `gobcoCounts.finish(0)`.
   - `instrumenter.go` `writeGobcoFiles`: write `gobco_single.go` when `regPath` is empty,
     `gobco_module.go` otherwise.
4. Replace the package-level variables:
   - `instrumenter` gets fields `importer types.Importer`, `regPath string` and `statsName string`
     (the package's name in its stats files). `resolveTypes` uses
     `i.importer` when set, otherwise the upstream line
     `importer.ForCompiler(i.fset, "source", nil)`.
   - `gobco` gets fields `module bool`, `exclude []string`, `threshold float64`.
   - Delete `sharedImporter`, `regPath`, `exportFiles`, `overlayDir`.
   - `newInstrumenter()` stays; `runModule` sets the two new fields on each instance.
5. `main.go` `parseOptions`: remove `-overlay`. Add `-module` (bool), `-exclude` (repeatable, same
   `newSliceFlag` as `-test`), `-threshold` (float, default 0 = off). `gobcoMain` calls `runModule`
   when `g.module` is set.
6. `main.go` `parseArgs`: in module mode skip `classify` and keep the raw arguments, default
   `./...`. Single mode keeps the `len(args) <= 1` assertion. `module.go` `listPackages`, used for
   the package arguments and for `-exclude`: a pattern whose first path element is an existing
   directory and that does not start with `.` or `/` gets the prefix `./`, so `internal/...` means
   the directory and not the standard library.
7. `module.go` `runModule`: implement the flow in Architecture, steps 1–7. Errors:
   - `go list -m` prints more than one line: `gobco: -module needs exactly one module`.
   - `<module root>/gobcoreg` exists: `gobco: directory gobcoreg already exists`.
   - no package matched: print `nothing to instrument`, exit 0.
   - a matched package is outside the module: `gobco: package <dir> is outside the module`.
   - `-exclude` matches no package: `gobco: -exclude <patterns> matches no package`.
   - `go test` fails: print the report, exit 1.
   - a stats file with a different number of conditions than the baseline: error naming the file.
8. Report, one function used by both modes, in this order:
   - blank line, then `Branch coverage: 3/4 (75.0%)` or `Condition coverage: …`; `0/0` prints
     `(100.0%)`
   - one line per uncovered condition, through the existing `printCond`
   - `Per-package coverage:` with `  <package dir>: covered/total (pct)`, only when more than one
     package is reported
   - `Per-file coverage:` with `  <file>: covered/total (pct)`, in first-seen order; the file is
     `Start` without its last two `:n` parts

   In module mode `Start` is the path relative to the module root.
9. Threshold, both modes: when `covered*100 < threshold*total`, print
   `gobco: coverage 97.5% is below the threshold 98.0%` to stderr and exit 1.
10. `templates/gobco_fixed.go`: `TrueCount` and `FalseCount` become `int64`; `cover` increments
    them with `atomic.AddInt64`. `main.go` `condition` gets `int64` fields too.
11. Add `testdata/module` (own `go.mod`: `module example.com/gobcomod`, `go 1.16`):
    - `b/b.go`: `Positive(x int) bool` with `if x > 0 && x < 100 { return true }; return false`.
      No tests. The compound condition makes branch mode and condition mode give different figures.
    - `a/a.go`: `Check(x int) bool` that calls `b.Positive(x)` as a statement, then
      `if x < 0 { return false }; return true`.
    - `a/a_test.go`: calls `Check(5)` from two parallel subtests.
    - `it/it_test.go`: its own `TestMain` ending in `os.Exit(m.Run())`; one test calls `Check(0)`.

    Then `module_test.go` with the cases in Testing Strategy.
12. Update the `coverage: N/M` expectations in `main_test.go` to the new format and add the
    per-file lines the tests now see. README: install path, a "Module mode" section with the command
    line above and an example, and a line that this is a fork of `rillig/gobco`.
    Remove the two upstream badges and `.travis.yml`.
13. `main.go`: `gobco` gets its own `check` that prints the error, calls `cleanUp` and exits with
    status 1, so a run that stops on an error leaves no temporary files. `module.go` `goList`: a
    failed `go list` stops with `gobco: go list: <err>` after the output of `go list` itself.
14. `go.mod`: `go 1.27`. `.github/workflows/go.yml`: `go-version: '1.27'`. README: gobco needs
    go1.27 or later.
15. Verify on a real service module with integration tests (see Testing Strategy, manual).

## Testing Strategy

Command: `sh ./test.sh` (runs `go test ./...`, installs gobco and runs it on itself). All upstream
tests must pass.

`module_test.go`, each case changes into `testdata/module` and calls `RunMain`:

| Case | Arguments | Expect |
|---|---|---|
| cross-package and cross-process merge | `-module` | exit 0; `Condition coverage: 4/6 (66.7%)`; `a/a.go:…: condition "x < 0" was 3 times false but never true`; `b/b.go: 3/4 (75.0%)`; `a/a.go: 1/2 (50.0%)` |
| branch mode | `-module -branch` | `Branch coverage: 3/4 (75.0%)`; `b/b.go: 2/2 (100.0%)` |
| exclude | `-module -exclude ./a` | `Condition coverage: 3/4 (75.0%)`; no `a/a.go` line |
| patterns without `./` | `-module -exclude a a b/... it` | same as the exclude case |
| threshold fails | `-module -branch -threshold 80` | exit 1; stderr has `below the threshold 80.0%` |
| threshold passes | `-module -branch -threshold 75` | exit 0 |
| race | `-module -test -race` | exit 0; no `DATA RACE`; skipped when `CGO_ENABLED` is not 1 |
| explicit packages | `-module ./b` | `Condition coverage: 0/4 (0.0%)`: only `b` is instrumented, so nothing flushes |
| working tree untouched | after a run | the file list of `testdata/module` is the same as before |
| errors | `-module fmt`; `-exclude nonexistent`; a `go.work` with two modules; a module with a `gobcoreg` directory | exit 1 with the message from task 7 |
| a test fails | a temporary module with a failing test | exit 1; the report is still printed |
| a package does not compile | a temporary module with an undefined name | exit 1; stderr has the compiler's message and `gobco: go list: exit status 1` |
| stop on an error | `g.check` with an error | exit 1; the temporary directory is gone |
| argument parsing | `-module` with and without packages | `./...` by default, otherwise the arguments as given |

Single mode: one new case, `-threshold 100` on `testdata/issue38` (its tests pass, so only the
threshold can make the run fail), exit 1.

Manual, on a real service module that has integration tests in a directory with its own `TestMain`,
gobco built with the Go toolchain of the environment that runs the tests:

```
time gobco -module -branch -exclude ./internal/<excluded>/... ./internal/... ./test/integration
```

Expected: the same figure as the prototype gave on that module, in about the time of a plain
`go test` run. Different numbers are a finding to report, not something to tune.

## Platform-level tests

None. gobco is a developer tool with no service contract.

## Edge Cases & Error Handling

| Case | Handling |
|---|---|
| Test directory with its own `TestMain` | Pass it as a package argument; the existing `instrumentTestMain` wraps `os.Exit` |
| Test package that is not instrumented | Its binary does not flush; hits made only from it are lost. Shown by the `explicit packages` test |
| Package with no conditions | Counted as 0/0; it has a line in the per-package list and none in the per-file list |
| Package no test links | Counted from the baseline as uncovered |
| `go list -test` variants (`p [p.test]`) | Skipped when building the export map |
| `package x_test` using `export_test.go` symbols | Type check fails with gobco's existing error. Not handled: no module it is meant for has such a file today |
| `go.work` with several modules | Error, see task 7 |
| A package does not compile | The run stops with the compiler's message, see task 13 |
| gobco stops on an error | The temporary directory is removed first, unless `-keep` is given |
| Module built with an older Go than gobco | Not handled and not tried: gobco reads the export data that the module's toolchain writes |
| Pattern without `./`, such as `internal/...` | Read as a directory of the module, see task 6 |
| `-stats` in module mode | Ignored; module mode keeps its stats files in the temporary directory |
| `go vet` on the overlay-only registry package | `-vet=off` is always passed in module mode |
| `-immediately` with parallel tests | Still not safe for concurrent writes, as upstream |
| Binary built with another toolchain | Not handled in code; README says to build gobco where the tests run |

## Acceptance criteria

- `gobco -module` on a service module finishes in about the time of a plain `go test` run.
- Its branch figure includes integration tests and equals the figure the prototype gave.
- gobco's own test suite passes, single-package mode included.
